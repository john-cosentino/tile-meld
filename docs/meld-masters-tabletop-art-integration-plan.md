# Meld Masters — Staged future tabletop art-integration plan

Five mandatory, explicitly-gated checkpoints for wiring **approved** art
assets into the static tabletop concept prototype, once they exist under
`apps/web/src/assets/tabletop-production/`. **None of this work has
started.** This document exists so that when it does start, it happens
in small, reviewable, stoppable steps — never as one large uncontrolled
integration pass.

Each checkpoint corresponds to a generation batch in
`docs/meld-masters-chatgpt-art-production-handoff.md` /
`docs/meld-masters-chatgpt-art-generation-prompts.md`. Do not begin a
checkpoint until the assets it needs are both generated by ChatGPT *and*
approved by the user in the asset lab (`/prototype/tabletop-assets`).

## Checkpoint A — Masthead

**Prerequisite:** `wordmark-meld-masters.png` approved in the asset lab.

**Work:**
- Integrate only this one approved asset into `ConceptBrandMark.tsx`
  (see the integration contract's wordmark section for the exact
  mechanism).
- No other component changes.

**Capture:**
- Regenerate all four raw screenshots (`prototype--desktop-1440x900.png`,
  `prototype--desktop-1280x720.png`, `prototype--phone-390x844.png`,
  `prototype--phone-landscape-844x390.png`) via
  `e2e/scripts/capture-tabletop-static-prototype-v2.ts` (or a v3 script,
  matching the existing naming pattern).
- Regenerate the matching `comparison--*` and `overlay--*` pairs.

**Stop for user approval on:**
- Does the illustrated wordmark read clearly at all three sizes in situ
  (not just in the asset lab's isolated preview)?
- Does it visually anchor the rest of the still-CSS-only cabinet
  reasonably, or does it now look mismatched against the flatter
  board/rack/sidebar (a legitimate reason to hold this checkpoint open
  until Checkpoint B lands, rather than treating A as fully "done")?

## Checkpoint B — Board and rack

**Prerequisite:** all three `board-frame-*.png` variants and
`rack-frame.png` approved in the asset lab.

**Work:**
- Integrate only these four approved assets into `ConceptBoard.tsx` and
  `ConceptRack.tsx` (background-image + `background-size:100% 100%` for
  the board variants, nine-slice `border-image` for the rack — see the
  integration contract).
- No other component changes.

**Capture:**
- **Critical check first, before any screenshot:** open each of the
  three layouts live and confirm every tile number is still perfectly
  undistorted and legible over the new board background — this is a
  hard requirement, not a nice-to-have (see the handoff doc's board
  rejection criteria).
- Regenerate all four raw screenshots, comparisons, and overlays.
- Regenerate **all three silhouette comparisons** — this batch is the
  one most likely to move the blurred-massing test's result, since the
  board is the single most visually dominant region on every layout.

**Stop for user approval on:**
- Tile text legibility (non-negotiable — reject and revert if compromised).
- Taper angle reads correctly and consistently across all three layouts.
- Rack reads as physically attached to the board, not floating or
  seamed.

## Checkpoint C — Competitor rail and sidebar

**Prerequisite:** whichever of `competitor-card-frame.png`,
`competitor-active-overlay.png`, `sidebar-panel-frame.png`,
`countdown-screen-bezel.png`, `mascot-tip-icon.png` were pursued and
approved (all optional — this checkpoint may be a no-op if none were
pursued, and that's a fine outcome, not a failure).

**Work:**
- Integrate only the approved subset into `ConceptCompetitorRail.tsx`
  and `ConceptSidebar.tsx` / `ConceptPhonePortraitLayout.tsx`'s
  support-row.
- Live portraits (`portraitForSeat(...)`), names, scores, tile counts,
  turn status, countdown digits, move-log entries, and tip text must all
  visibly survive integration completely unchanged in content and
  position — only their background frame changes.

**Capture:**
- Regenerate desktop + phone-portrait + phone-landscape comparisons and
  overlays. A full silhouette re-run isn't necessary here (these are
  already the closest-matching regions per the v2 test) unless the
  active-overlay asset visibly changes the rail's overall massing.

**Stop for user approval on:**
- The neutral competitor-card frame recolors correctly per seat via the
  existing CSS accent mechanism.
- No live text (name/score/move-log/tip) is now less legible than before
  integration.

## Checkpoint D — Controls

**Prerequisite:** `action-plate-cyan.png`, `action-plate-purple.png`,
`action-plate-gold.png` approved (required); `action-plate-states.png`
and `action-icons-illustrated.svg` approved if pursued (optional).

**Work:**
- Integrate the three (or five) approved assets into
  `ConceptActionBar.tsx`.
- Preserve every existing icon/label/sublabel exactly as-is unless
  `action-icons-illustrated.svg` is specifically being swapped in.
- **If and only if** this is also the moment the prototype's action
  elements become real `<button>`s (a decision independent of the art
  itself — see the integration contract's native-controls note): confirm
  keyboard `Tab` reaches every button in the same left-to-right,
  top-to-bottom order as today, and that each one's native focus outline
  renders visibly above the new background art.

**Capture:**
- Regenerate all four comparisons. Specifically eyeball the action row's
  visual weight relative to the now-more-detailed board/rack/masthead
  above it — a common failure mode at this stage is the buttons now
  reading as *under*-weighted next to a richer cabinet above them.

**Stop for user approval on:**
- Commit Turn reads as visibly the strongest of the four actions.
- Nine-slice stretches cleanly at all three layouts' differing button
  sizes (no corner smearing or visible seams).
- Keyboard focus remains visible (if native buttons were introduced this
  checkpoint).

## Checkpoint E — Final static-prototype review

**Prerequisite:** every checkpoint above that the user chose to pursue is
complete and individually approved.

**Work:** none — this is a review-only checkpoint, not an integration
step.

**Capture:**
- Regenerate **all** raw screenshots.
- Regenerate **all** side-by-side comparisons.
- Regenerate **all** overlays.
- Regenerate **all** silhouettes (desktop, phone-portrait, phone-
  landscape).
- Compare the final result against `meld-masters-concept-01.png` and
  `meld-masters-concept-04.png` directly, region by region, the same way
  the v2 refinement pass did.

**Stop for user approval on:** the whole composition, holistically — does
it now read, at a glance, as the same interface as the concept art. This
is the last stop before any conversation about live-game integration.

**Do not begin live-game integration (wiring this prototype's components
or assets into the real `TabletopPage.tsx`) without explicit, separate
user approval after this checkpoint.** That is a distinct decision from
"the static prototype's art now matches the concept," made deliberately
later, not a default next step.

## What every checkpoint has in common

- One checkpoint's assets are integrated at a time — never combine two
  checkpoints' worth of changes into one commit.
- Every checkpoint ends with regenerated visual evidence, not just a
  code diff — "the code looks right" is never the acceptance bar; the
  screenshots are.
- Every checkpoint stops for explicit user approval before the next one
  starts. A checkpoint with no assets approved yet (e.g. Checkpoint C, if
  its optional assets are never pursued) is a valid, permanent stopping
  point — nothing forces later checkpoints to happen.
